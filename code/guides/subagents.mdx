## Subagents

Aristra Code can hand part of a task to a subagent: an agent with its own context that works in the background and reports back. Use it to keep a large search out of the main chat, or to run several investigations at once. Ask for it ("look into these three modules in parallel"), or let Aristra Code decide.

| Built-in type | For |
|---|---|
| `general-purpose` | Any task, with every tool a background agent may use |
| `Explore` | Read-only searching across a codebase |
| `Plan` | Read-only planning: designs an approach and the files involved |

Each subagent works in the chat's folder, with its mode and model (unless the call names another), and can start subagents of its own up to three levels deep. Up to 20 run at once in a chat, counting its agents' own agents. Its approvals are asked in your chat, the one at the top of the chain, naming the agent.

**What you see.** The status line counts running agents ("2 local agents"), and `/tasks` lists them with a few words on what each is doing. Enter opens one, and what you type there goes to that agent. When one finishes, the chat gets a line with its summary, and Aristra Code reads the result and carries on.

## Fork a chat

```text
/fork write the migration for the new schema
```

A fork is a subagent that starts with this chat's full context, so it needs no briefing. It does the one thing you ask and reports back while you keep working here. To carry on in a copy of the chat yourself, use `/branch` instead.

## Custom agents

A Markdown file in `~/.aristra/agents/` (every folder) or `.aristra/agents/` in a project (once you trust it) adds an agent type, in the same format as Claude Code's:

```markdown .aristra/agents/migration-reviewer.md
---
name: migration-reviewer
description: Reviews database migrations for locking, data loss and rollback safety
tools: read_file, grep, glob, shell
model: sonnet
---

You review database migrations. For each migration, check ...
```

| Field | Meaning |
|---|---|
| `name`, `description` | The agent's name, and what it is for (shown to the model). A file without either is skipped |
| `tools`, `disallowedTools` | Which tools it may use. `mcp__server` names a server's tools |
| `model` | `inherit`, `sonnet`, `opus`, `haiku`, `fable` (these four only when the chat is on a Claude model) or a model id |
| `effort` | Its reasoning effort |
| `permissionMode` | The mode it runs in, unless your chat is in `acceptEdits`, `auto`, `bypassPermissions` or `plan`, which it keeps |
| `maxTurns` | A limit on its model rounds |
| `isolation` | `worktree` to give it its own git worktree |
| `skills`, `hooks`, `mcpServers`, `memory` | Skills it loads, hooks active while it runs, its own MCP servers, and a memory folder of its own |
| `initialPrompt` | Put before your first message when a whole chat runs as this agent |
| `color` | Its color in lists: red, blue, green, yellow, purple, orange, pink or cyan |
| `omitClaudeMd` | `true` leaves out the folder's instruction files |

The body is its system prompt. A project's agent overrides yours of the same name, and your organization's overrides both.

### Run a whole chat as an agent

`aristra --agent migration-reviewer` starts a chat that runs on the agent's prompt, tools and model. In Aristra Desktop, the **+** menu of a new Code chat lists your agents as **Run as …**. The `agent` setting makes one the default for new chats.

## Worktrees

A subagent with `isolation: worktree` gets its own git worktree under `.aristra/worktrees/agent-<id>`, so parallel agents never edit the same files. When it finishes, a worktree it didn't change is removed; one it changed is kept, and its path and branch come with its report.

## Messages between chats

Aristra Code can send a message to a subagent, and to your other Aristra chats on this computer that are open or working right now, by name. Ask "tell the chat working on the API that the schema changed". The message arrives in that chat marked as coming from another chat. A chat in a different permission mode than the sender's doesn't take the message, and the sender is told.

## Workflows

For large fan-outs ("review every package", "research this from several sides"), ask for a workflow. Aristra Code writes a short script that runs many agents in a fixed order: in parallel, in phases, or as a pipeline. A run asks first, showing its description and phases (Ctrl+E shows the script), unless a rule allows it (`workflow(<name>)` for a saved one) or your mode doesn't ask. In Auto mode the reviewer decides.

- A run executes in the background, up to 16 agents at once, or two fewer than your computer's CPU cores when that is less.
- `/workflows` shows each run's phases and agents as they go, with keys to stop, pause, retry or skip an agent, and **s** to save the script as a named workflow.
- Saved workflows live in `~/.aristra/workflows/` or a project's `.aristra/workflows/`, and run as `/<name> args`.
- Aristra Code ships `/deep-research <question>`: it searches the web from several sides, has skeptics check every claim, and writes a cited report.

`disableWorkflows: true` (or `enableWorkflows: false`) in your settings, or `ARISTRA_DISABLE_WORKFLOWS=1`, turns workflows off.
